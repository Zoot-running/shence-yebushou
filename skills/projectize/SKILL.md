# projectize —— 项目化调度（POC v1，CTF 先行）

> 方法论三件套的 agent 可用压缩版（源头：军机 METHODOLOGY/ 三文档）。
> 核心理念：**计划是交付物，先审后做；并行是结构不是口号；教训必分类落账。**

## 一、立项书五槽（开打前写齐，缺一不开工）

1. **目标**：唯一硬指标 + 字典序次要项（例：满分 > 用时 > 花费）；非目标也写清（不做的事）。
2. **约束**：硬约束（红线合规/预算/时间窗）与软约束分开列。
3. **验收口径**：done 定义 + **停止条件**（什么时候算失败，与成功一起定义）。
4. **规则域**：任务的红线是什么——开工前识别（托管规则/私知边界/平台纪律）。
5. **假设日志**：把即将"猜"的东西显式写出来（`假设1：目标是X——如有误请纠正`），逐条供用户确认。

变更条款：目标/红线变了 → **基于当前已完成工作重新立项排计划**，旧计划作废，不续行。

## 二、计划评审（派活前自审——六要素缺一即重写）

计划必须含：
1. **依赖图（DAG）**——无依赖即可并行；没有图就没有并行依据；
2. **关键路径**——最长串行链=用时下限，标出来看能否再拆；
3. **并行扇出与汇聚点**——每条并行分支写明谁在何时综合/消歧；
4. **资源上限与证明**——并发上限/配额/预算显式列出并证明不超限；宽度免费处开满（思路征集），受限处给最高价值路径（3 容器）；
5. **执行者分工**——你排计划/调度/验收，**不下场解题**（唯一例外：执行者已交 FLAG_CANDIDATE 的临门一脚，≤3 工具调用）；
6. **验收与停止条件**——每任务 done 定义 + 总停止条件。

自审六问（逐条过）：有依赖图吗？有"可并行却排成串行"的吗？每条并行有汇聚点吗？资源上限写了吗会超吗？哪条我要亲自做、理由是什么？验收口径写了吗？

## 三、复盘分类（战后，四栏四桶）

- 四栏：**预期 vs 实际** / **决策-结果对照**（选项→选了啥→结果→反事实）/ **根因**（提示词/机制/平台/环境）/ **教训分类**。
- 四桶：**A 通用方法论 → 升格进 SKILL 合规层**（先验证再固化）；**B 机制先验/题源启发 → 本地私知档案**（不进托管 run prompt）；**C 一次性事实 → 归档战报**；**D 平台缺陷 → 反馈文档**（留证充分）。
- 成败同权重：败仗复盘更值钱。

## 四、评审分层（托管全自动模式）

- 开打前：立项书人工审定（唯一人工闸门，不烧钟）；
- run 中：本技能自审 + 机制校验，**零人工**；
- 战后：人工回审"计划 vs 实际"，纠正分类桶。

## 五、反模式速查（实测实证，撞上即纠）

串行亲挖 / 无汇聚的并行（报告洪水）/ 无上限的扇出 / 计划不含停止条件 / 计划与资源账脱节 / "平台坏了"当放弃借口（先重试/重开/换入口/留证，判死是最后且需留证的结论）。
